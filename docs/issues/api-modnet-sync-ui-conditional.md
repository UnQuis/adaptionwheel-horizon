## Use-case из adaptionwheel
Для порта нужны (в зависимости от скоупа MVP/MVP+):
- server-authoritative синхронизация состояния/прогресса/активации колеса и выбранных адаптаций клиенту (для HUD/индикации/экрана колеса);
- клиентские intents/запросы к серверу (например, активация/выбор/действия колеса) с валидацией на сервере;
- минимально достаточный UI feedback path (HUD/toast/overlay/message/mod screen hooks) для отображения прогресса, разблокировки, активного состояния и ошибок/ограничений.

## Что проверено/известно в Horizon (по доступным материалам)
- Низкоуровневый канал mod messages (`horizon:mod_net`, до 30 KB, лимиты по тикам/игроку, channel format `mod_id:name`) и send/receive hooks описаны в Horizon docs; в target-era кодовой базе присутствуют реализации/хуки (см. `native-hooks.json`, `crates/horizon-client/src/game/native_net.rs` в Horizon).
- В каталоге hooks/helpers есть UI/input/screen/HUD/mouse/key механизмы (`mod_screen*`, `mod_key`, HUD/screen hooks и др.), достаточность которых для конкретного UX порта требует прототипа.
- В native adaptation core порта сетевой protocol ещё не реализован/не подтверждён на уровне удобного и стабильного mod-API контракта.

## Почему текущих возможностей может быть недостаточно (условно)
- Rust mod-API для native модов не предоставляет удобный/документированный доступ к mod_net send/receive (или сигнатуры/жизненный цикл неудобны/нестабильны) на целевом build.
- Нет достаточного контракта для надёжного UI feedback (обновление HUD/экрана из состояния мода, жизненный цикл, threading/side ограничения, доступ к данным клиента).
- Ограничения канала (размер/частота/ordering/надёжность в нужных сценариях) мешают передаче необходимого состояния без хрупкой фрагментации/доп. протоколов.
- Требуемый UX колеса/индикации не реализуем через существующие hooks без значительных обходов или внутреннего API.

Если mod_net + существующие UI hooks достаточны для выбранного MVP-среза, issue не подавать (зафиксировать рабочий паттерн в docs).

## Предлагаемая точка расширения (минимально необходимая, по результатам прототипа)
1. **Стабильный native mod API для mod messages:** явные host/helper bindings для send/receive, документация стороны/потока/лимитов/ошибок, примеры.
2. **Документированный UI feedback контракт:** минимальные helper/hooks для HUD/overlay/toast/mod-screen обновлений на клиенте из mod state/sync событий.
3. **Опционально (если потребуется):** вспомогательные утилиты сериализации/версии протокола или более высокоуровневый state-sync helper для модов.
