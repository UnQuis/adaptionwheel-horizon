# Feature Parity Matrix — adaptionwheel → Horizon port (PR-0 draft, Agent #1)

> Основано на анализе исходников `adaptionwheel` (NeoForge 1.21.1, mod 0.1.6) и требованиях MVP.  
> Статусы Horizon API/движка на этапе PR-0 считаются **уточняемыми**; в колонке заметок отмечены риски/неизвестные точки интеграции.

## MVP (минимальный end-to-end)
**Цель MVP:** игрок может экипировать/активировать колесо, мод отслеживает и сохраняет состояние адаптаций, обрабатывает 3–5 базовых сценариев, показывает базовую индикацию и восстанавливает состояние после релога.

**Предлагаемые 3–5 сценариев для MVP:**
1. **Env_Fire** (окружение/урон огнём): получение огненного урона запускает/ускоряет анализ → завершение даёт иммунитет/состояние "adapted".
2. **Env_FallDamage** (падение): накопление урона/событий падения → адаптация к падению.
3. **Type_EXPLOSION** или другой базовый `Type_*` (урон, leveled): несколько получений урона повышают уровень/снижают урон.
4. **Move_PowderSnow** или **Move_SoulSand** (движение/поверхность): взаимодействие со средой даёт одноразовую адаптацию.
5. *(опционально в рамках MVP, если просто реализуется)* **Contact_minecraft:zombie** (контакт с мобом): базовый entity/contact сценарий без полного entity/existence графа.

## Рекомендованный срез MVP (реализация)
1. **Скелет мода + item/activation**: колесо как предмет и признак активного состояния (через эквивалент слота/экипировки Horizon).  
2. **State model + persistence**: `PlayerAdaption`-подобное ядро (минимальные поля) + сохранение/загрузка после релога (player-bound; item-bound опционально).  
3. **Analysis engine (minimal)**: задачи, таймер/прогресс, завершение, лимиты/простая конфигурация.  
4. **3–5 adaptation scenarios**: fire/fall + 1 тип урона + 1 движение/поверхность (+ опционально простой contact).  
5. **Sync + indication**: сервер → клиент обновление состояния/прогресса, минимальный HUD/уведомление.  
6. **Dev commands (минимум)**: status/reset/grant для ускорения проверки.

## Главные риски/зависимости для порта
- **Horizon API parity**: события (урон, тик, движение, взаимодействие с блоками/мобами), экипировка, persistence, сеть, UI/GUI, эффекты/атрибуты.
- **Сохранение инвариантов оригинала**: merge vs replace при загрузке состояния, `active` vs `adapted/level`, server-authoritative мутации.
- **Mixins/низкоуровневые хуки**: многие механики в оригинале завязаны на Mixin/NeoForge internals; часть придётся переосмысливать.
- **Клиентский объём**: кастомные экраны, 3D-рендер OBJ, шейдеры/FX — высокий риск по трудозатратам, не для MVP.
- **Контентные data pipelines**: domain_altar, advancements, worldgen, рецепты/лут — переносить поэтапно после ядра.
